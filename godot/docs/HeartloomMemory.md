# 心织记忆（Heartloom Memory）

心织记忆是 Spring Haven Companion Core 自有的本地长期记忆系统。它不加载、
调用或同步外部记忆插件，也不要求第三方机器人框架运行。

## 为什么叫“心织”

系统不会把完整聊天记录直接塞回模型，而是把分散的经历、关系、偏好和家庭规则，
按当前话题重新“编织”为本轮需要的记忆。它包含两类内容：

1. 对话自动形成的经历记忆，例如主人表达过的偏好、身份和约定；
2. 用户手工维护的心织条目，作用类似 Worldbook/Lorebook。

## SQLite 数据边界

默认数据库为 `companion-core/user_data/heartloom.sqlite3`，只保存在本机并被 Git 忽略。
数据库启用 WAL、外键、5 秒 busy timeout 和索引化触发词。记忆没有条数上限，也不会
因为 `/session/reset` 被删除。

数据库保存：

- 带时间戳的共享对话事件；
- `*` 家庭共享或指定角色私有的记忆；
- 类型、重要度、置信度、情绪倾向和时间半衰期；
- 触发词、常驻状态、优先级、召回次数；
- 对话影响、行为提示和行为标签；
- 请求幂等结果与当前会话序号。

所有对话事件、记忆、离线生活状态与幂等结果都按 Godot 旅程的稳定 `save_id` 分区。
切换旅程不会删除或复制长期记忆；重新载入原旅程后，同一 `save_id` 会重新关联原有
Heartloom 数据。

时间衰减只降低普通经历的召回权重，不物理删除数据。身份、重要关系或手工条目可以将
`half_life_days` 设置为 `0`，表示不随时间衰减。

## 召回方式

Heartloom 为中英文建立本地关键词索引。中文会生成二至四字的 n-gram，因此不依赖云端
Embedding 也能召回“栀子花”“晚饭约定”一类内容。候选记忆按以下因素排序：

- 当前文本与触发词/内容的重合度；
- 手工条目优先级；
- 记忆重要度与置信度；
- 距离上次更新的时间及半衰期；
- 过去被成功召回的次数。

召回结果写入动态 `<heartloom_memory_context>`，不会改变稳定 Persona System Prompt，
有利于 DeepSeek 的前缀缓存。角色不会看到数据库字段，也不应逐条复述召回内容。

## 角色独立的整理提示词

小玲和小奈分别使用独立文件：

- `companion-core/user_data/memory_prompts/ling.md`
- `companion-core/user_data/memory_prompts/nai.md`

文件路径由 `roles.json` 的 `memory_prompt_file` 指定，未来自定义角色也可以携带自己的
整理提示词。小玲的默认版本更重视可靠承诺、家庭空间和克制表达下的真实关心；小奈的
版本更重视陪伴、情绪变化和共同生活习惯，但会避免把热情回应夸大成永久事实。两份提示
都强制区分自己的经历、另一位角色的经历和主人转述。

主聊天回复完成后，Organizer 在后台运行，不阻塞聊天框。它最多提取三条结构化长期
记忆；如果输出无效、网络失败或进程中断，确定性保底记忆仍然存在。寒暄等低信息量回合
不会额外调用 LLM，只显示“本轮略过”。可在配置中关闭：

```json
{
  "memory_organizer_enabled": false
}
```

也可以临时设置 `SPRING_HAVEN_MEMORY_ORGANIZER=false`。

### 缓存策略

Persona、角色边界、Heartloom 规则和每个角色的 Organizer Prompt 都是不含日期、数值和
本轮状态的稳定 System 前缀。身体状态、共享历史、召回结果和当前文本只进入动态 User
消息。系统不会为提高缓存率删除必要历史或记忆；当缓存率与回答质量冲突时，以回答质量
和角色连续性为优先。

`GET /memory/status` 会返回最近一次 Organizer 的 `input_tokens`、`output_tokens` 和
`cached_tokens`，便于在不改变提示词的前提下观察真实缓存效果。

## 记忆网络

聊天页顶部的“🕸️”会打开交互式心织记忆网络。每个节点是一条长期记忆，节点大小表示
重要度，金色、青绿色和粉色分别表示家庭共享、小玲和小奈作用域。画布支持拖动节点、
平移、滚轮缩放、精确角色筛选、标题/内容搜索和关联强度过滤；选择节点后会显示原文、
时间、主题及其关联记忆。

`GET /memory/graph` 在本机按需计算关系，不新增数据库表，也不会调用 LLM。连线综合共享
索引词、触发词、同一来源事件和时间邻近度，并在每条边返回可解释原因。系统使用 IDF
降低“主人”“对话”等全库常见用语的权重，限制节点数、总边数和单节点度数，保证长期
运行后的图谱仍可交互。搜索或记忆内容发生变化后重新打开/刷新即可得到新网络。

## Worldbook 式影响

手工条目支持：

```json
{
  "influence": {
    "dialogue": "谈到花时语气更温柔。",
    "behavior_hint": "盆土变干时优先照顾花。",
    "behavior_tags": ["care_plant"]
  }
}
```

`dialogue` 影响措辞和态度；`behavior_hint` 影响高层行动选择；`behavior_tags` 会随
`/chat` 响应返回，供生命模拟和未来的通用行为规划器消费。它们不能越过 Godot 的本地
动作白名单、导航和物理校验。

如果场景提交 `spring_heaven.scene_actions.v1` 上下文，核心可以从模型回复中提取一个
高层动作，并按上下文中的动作和目标白名单严格校验；坐标、速度和节点路径始终留在
Godot 内部。

## 双角色会话编排

现有 Godot 对话框继续采用已经验证的顺序链路：第一位回复保存后，第二位才开始生成，
因此她能看到第一位刚刚说的话。Heartloom 又把这条共享历史持久化到 SQLite，即使核心
重启也能补齐 Godot 未携带的近期上下文。

新的 `POST /orchestrate` 提供核心级编排：

- 明确提到一位角色时由她回复；
- “你们都回答”或 `reply_mode=both` 时按选中角色优先顺序生成；
- 两个名字同时出现但没有双人指令时保持当前选中角色；
- “小玲去问小奈”建立 origin/target 路由，不会生成“小奈去问小奈”；
- 所有普通消息默认对房间内角色可见；
- 编排不会自动切换用户当前选择的角色。

## 管理与备份

可以使用 `companion-core/tools/heartloom_memory.py` 导入、列出、模拟召回、导出和删除
心织条目。`config/heartloom_entries.example.json` 是可直接导入的格式示例。

备份时可复制 SQLite 主文件及 `-wal`、`-shm` 文件，或者先停止 Companion Core 后只
复制 `heartloom.sqlite3`。未来的 Workshop 角色包应只携带明确选择导出的手工条目，
不能打包玩家的自动经历和聊天事件。
