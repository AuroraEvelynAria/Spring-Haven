# ADR: 统一结构化输出信封规范(含 `STATE_DELTA` 速率闸门)

- 状态:**草案(仅设计,未实施)**;实现前需过评审
- 关联:issue #25(本单)、#22(Phase 2 依赖本规约)、#24(状态块位置)、#29(数值卫生硬性不变量)、#23(world_time 单时钟,本项的窗口口径依赖)
- 决策范围:`companion-core/src/spring_haven_core/` 的提示词组装(`prompting.py`)、输出解析(`scene_actions.py`、`organizer.py`),以及未来新增的 `state_delta.py`

## 背景

现状的**标记(marker)分两个方向**,输入侧由应用写入,输出侧由模型产出:

| 方向 | 标记 | 语法 | 解析位置 |
|---|---|---|---|
| 输入(应用→模型) | 运行状态块 | `<spring_haven_runtime_context version="1">` … `</spring_haven_runtime_context>` | `prompting.py:10-11` |
| 输入(应用→模型) | 记忆上下文块 | `<heartloom_memory_context version="1">` … `</heartloom_memory_context>` | `prompting.py:12-13` |
| 输出(模型→应用) | 场景动作 | `<scene_action>{严格 JSON}</scene_action>` | `scene_actions.py:9` 正则 |
| 输出(模型→应用) | 记忆整理器 JSON | `{"memories":[…]}`(独立调用) | `organizer.py:12` 契约 |

设计草案还要再加一个**输出标记** `<<STATE_DELTA>>`,让模型直接输出生理增量。
四套标记各自独立解析会立刻产生三类问题:

1. **嵌套** —— 模型可能在 `<scene_action>` 的 JSON 字符串里写出 `<<STATE_DELTA>>`,或反之;
2. **注入逃逸** —— 输入侧已有转义(`prompting.py:208-211`、`241-244`、`274-277` 维护着标记清单并在嵌入用户文本前转义),但**输出侧没有等价规则**;
3. **共存优先级歧义** —— 同一条回复既有 `scene_action` 又有 `STATE_DELTA` 时谁先结算?两者改同一字段时谁赢?

## 决策

### D1 单一解析器、单一信任源

- 输出侧只保留**一个**入口:`extract_response_envelope(text, state, role_id) -> (visible_reply, actions, state_delta)`。
- 现状 `scene_actions.py::extract_scene_actions()` 的返回形状 `(visible_reply, list[dict])` 是其超集子集,迁移时应保持**向后兼容**(旧调用点不改语义)。
- 信任源唯一:只有**应用追加的最后一个状态块**(输入侧)与**同一条回复内的解析结果**(输出侧)被采信;用户原文、引述历史、记忆条目中的同形标记一律无权覆盖 —— 这条与 #24 已落地的规则一致。

### D2 统一转义规则(输入侧已有,输出侧补齐)

- 输入侧:沿用现有标记清单转义。
- 输出侧:解析器必须先**剥离**全部标记,再返回可见文本。客户端已有回归护栏
  `ExplorationAIFlowCheck.gd:107`(断言 `not reply.contains("<scene_action")`),
  `<<STATE_DELTA>>` 必须复用同一条断言,不得只做服务端剥离。

### D3 共存优先级:先动作,后状态

单条回复内的固定解析顺序:

1. `<scene_action>` —— 确定性场景动作(应用白名单校验,失败可整条丢弃);
2. `<<STATE_DELTA>>` —— 生理增量;
3. 剩余文本 = 可见回复。

理由:`scene_action` 的合法性可被应用独立判定,而 `STATE_DELTA` 的互斥判定需要**已知本轮是否命中 `local_effect`**(见 D5),因此必须排在动作之后。

### D4 `STATE_DELTA` 契约

```
<<STATE_DELTA>>
{"role_id":"ling","deltas":{"hunger":-8,"mood":3}}
<<END_STATE_DELTA>>
```

- `role_id` 必须命中白名单(`RoleRegistry.ids()`);未知角色**整块丢弃**;
- 字段白名单:与 `prompting.py:332-336` 的 `state_labels` 对齐(六项生理量 + `mood`/`stress`);
- 单字段**钳位** `[0,100]`;非有限数(NaN / Inf / 字符串 / 布尔)整字段丢弃;
- **可选语义** —— 模型不输出则不改状态;**格式异常不阻塞模拟**,降级为「本轮无增量」。

### D5 速率闸门(防小步绕过)

单次钳位拦不住「连续多轮各 +1」慢慢越界,故引入**累积净变化速率闸门**:

- 粒度:`(role_id, stat)` 二元组;
- 窗口:每 **1 世界小时** —— 注意按 #23 的 `world_time` 计,不是现实小时;
- 语义:窗口内该字段**所有增量之和**超过上限即触发处置(见未决项 1);
- 上限初值建议取「单次钳位幅度的 3 倍」,具体值待标定。

**与 `local_effect` 互斥**:确定性交互已由 `InteractionRules` 结算过的轮次,
`STATE_DELTA` 对**同一字段**必须忽略,避免双重结算(承 ADR-003 D5 的 `interaction_delta` 汇合点)。

### D6 与 #29 硬性不变量的一致性

- `STATE_DELTA` 是**写入指令**而非读取,解析出的数值**可以**进入状态容器;
- 但解析器的日志与事件记录**不得把数值回显进后续上下文** —— `state_events.delta_json` 仅用于调试,
  不进 prompt(与 ADR-002 的不变量一致)。

## 未决项(需用户裁决)

1. 超限处置:**整批丢弃**还是**截断到剩余额度**?(丢弃更安全,截断更平滑)
2. 速率上限的初值取多少?(需要一个标定实验)
3. 窗口边界用「世界小时的整数桶」还是滑动窗口?
4. `STATE_DELTA` 与 `scene_action` 允许共存,还是规定「一条回复只能二选一」?(共存更灵活,二选一实现更简单)
5. 解析失败是否需要一条 `state_delta_rejected` 事件用于排查?

## 备选方案(已否决)

| 备选 | 否决理由 |
|---|---|
| 各标记独立解析、各写一个正则 | 嵌套与优先级歧义无法靠分散代码解决,必然出现「谁先匹配谁赢」的不可预测行为 |
| 让模型直接输出完整状态快照 `{"hunger":72}` | 快照语义与后端权威衰减(#22/#23)冲突:模型不知道当前权威值,覆盖会造成状态跳变 |
| 用 JSON mode / function calling 替代标记 | 破坏 `visible_reply` 的自然语言流式体验,且本地各 provider 支持不一致 |
| 去掉 `STATE_DELTA`,只保留确定性交互结算 | 放弃了「LLM 参与状态演进」这一产品意图;但可作为降级路径保留 |

## 正面后果

- 四套标记收敛到一个解析器,嵌套 / 逃逸 / 优先级三类问题集中在一处解决。
- 速率闸门给了「LLM 自主改状态」一个可配置的**安全边界**,#22 Phase 2 才敢放开写权限。
- 输出侧转义规则补齐后,客户端既有断言可直接复用为回归护栏。

## 负面后果

- 提示词需新增 `STATE_DELTA` 格式说明,挤占上下文预算(需与 #24 的尾部块一起核算)。
- 速率闸门引入「模型输出被静默丢弃」的可能;若不记录事件,排障会非常困难。
- 世界小时窗口使本项与 #23 强耦合:**#23 未收尾前不应实现**(周键与窗口口径还会漂移)。

## 验收

- 规约文档(本 ADR + 提示词段落)+ **注入用例**:用户伪造标记 / 不完整标记 / 重复标记 / 嵌套标记,四类均不得改变状态。
- 速率闸门单测:窗口内累积超限被拦;窗口翻转后额度恢复;未知 role / 未知字段被丢弃;`local_effect` 命中轮次的同字段被忽略。
- 回归:`test_prompt_qualitative.py`(数值卫生门禁)必须仍全绿。
