# ADR: 离线驻留推演限流 —— 纯规则模拟 + LLM 调用延后合并

- 状态:**草案(仅设计,未实施)**;实现前需过评审
- 关联:issue #26(本单)、#23(world_time 倍率,本项的直接诱因)、#22(后端真相源)、#25(结构化输出信封)、#27(会话层);`godot/docs/CompanionCoreReliability.md`
- 决策范围:`companion-core/src/spring_haven_core/service.py` 的调度循环(`run_due_digests` / `run_due_weekly_insights` / 角色社交)、`app.py:930+` 的调度器挂载点、`memory.py` 的 `world_now()`

## 背景

现有设计只排除了**「关机后回溯」**(即不补算停机期间的世界时间),但**没有约束「驻留期间」的倍率放大**。

世界时间倍率(承 #23 的 `journey_clock.rate`)把「游戏内一天」压缩到现实几分钟。
而以下三类 LLM 调用挂在**世界时间**上:

| 触发性 LLM 调用 | 现状入口 |
|---|---|
| 每日 digest 归纳 | `service.py:558+`(Phase 1:把生活事件转成心织记忆) |
| 周反思 | `service.py:423 run_due_weekly_insights()` |
| 角色社交对话 | `LifeLabWorld.gd` 侧发起 → `service.py` 角色间生成 |

**问题**:`rate=60` 时,世界时间每前进 1 小时 = 现实 1 分钟。若调度按世界时间触发,
则 LLM 调用密度被倍率**线性放大** —— 现实里的一小时可能要跑 60 天份的 digest 与周反思。

当前 `rate` 默认 `1.0`,所以这个雷**尚未引爆**;一旦启用倍率(离线驻留模拟)立刻显形。
雪上加霜的是:离线驻留期间玩家**不在场**,这些调用产出的大量记忆没有任何人消费,
却照常消耗 provider 配额与费用。

## 决策

### D1 驻留期间 = 纯规则模拟,零 LLM

- 「离线驻留」模式(心跳停止超过阈值后 Core 自行进入,见 `CompanionCoreReliability.md:30`)
  下,**禁止**任何 LLM 调用。
- 期间世界时间照常推进,**只**做两件纯规则的事:
  1. 生理衰减(已有:`memory.py::advance_life_decay()`,按 world_time 水位线推进);
  2. 事件日志追加(state_events / life_events,确定性规则生成)。

### D2 LLM 调用延后到玩家返回时合并批量生成

- 玩家返回(恢复心跳)时,把驻留期间**累积的事件日志**合并成**更少、更大**的批次:
  - 每日 digest:驻留 N 天 → 合并为**一次**归纳调用,输入是压缩后的事件时间线;
  - 周反思:若驻留跨越多个世界周,按周合并、但**单次响应上限**受 D3 约束;
  - 角色社交:降级为纯规则占位(记录「她们这段时间相处融洽」这类可解释摘要),不生成逐句对话。
- 合并质量要求:见验收 —— 返回时总结必须**可接受**,不得退化成流水账。

### D3 硬上限:限速队列

- 即使合并,仍需要一个**兜底硬上限**,形式为令牌桶:
  - 例如「每现实 15 分钟最多 1 次 LLM 调用」「返回时的首轮合并最多 M 次调用」;
  - 超出的批次进入队列,**按优先级**消化:周反思 > 每日 digest > 角色社交(越稀有越优先)。
- 上限是**配置项**(`core_config.json`),不与 `rate` 成正比 —— 这是本决策的关键:
  上限锚定**现实时间**,而模拟锚定**世界时间**,两者解耦。

### D4 与 #23 的依赖关系

- 本项的触发判定、批次边界、窗口口径**全部**基于 `world_time`;
- 但**限速令牌锚定现实时间**。这个「双时钟」划分必须显式写入文档,
  否则会被误认为又一个 #23 的现实时间残留。
- **前置**:#23 的周键与窗口口径收尾后,本项的批次边界才稳定。

## 未决项(需用户裁决)

1. 驻留判定阈值:沿用现心跳口径(缺心跳 ≥ 3 分钟且用户空闲 ≥ 30 分钟),还是另设?
2. 「可接受的合并总结质量」如何量化?(建议:抽样人工评审 + 与在线逐日 digest 的语义相似度对比)
3. 限速上限的具体值?(挂在哪个配置键)
4. 返回时首轮合并是同步阻塞(玩家等)还是后台异步(先给规则摘要,稍后补 LLM 版本)?
5. 角色社交在驻留期间**完全规则化**是否可接受产品体验?

## 备选方案(已否决)

| 备选 | 否决理由 |
|---|---|
| 驻留期间照常按世界时间触发 LLM | 倍率下调用密度线性爆炸,费用不可控,且产出无人消费 |
| 直接禁止离线推演(世界时间冻结) | 与 #23「离线倍率」的产品意图冲突,角色像被暂停了 |
| 只做限速、不做合并 | 限速会让积压无限增长;合并才是把 N 次调用压成 1 次的关键 |
| 限速上限与 `rate` 成正比 | 等于没限速 —— 倍率越高调用越多,正是要避免的失效模式 |
| 驻留期间保留 LLM 但用最便宜的模型 | 省了钱没省调用次数,仍受 provider 速率限制与上下文预算约束 |

## 正面后果

- 费用与调用次数**可预期**:上线倍率前先有硬上限。
- 离线驻留变成纯计算,Core 在无人值守时几乎不占网络与配额。
- 「返回时合并」天然产出**更大时间粒度的叙事**,与角色「过了一段时间」的体感一致。

## 负面后果

- 玩家返回瞬间可能有一波合并调用,首轮响应变慢(需 D4 未决项 4 的取舍)。
- 合并总结的信息密度低于逐日 digest,可能丢细节(需验收守住质量下限)。
- 引入「双时钟」概念(模拟=世界时间,限速=现实时间),认知成本上升,必须写文档。

## 验收

- 倍率 `60x` 驻留 **8 小时**(世界时间推进 20 天)的模拟中,**LLM 调用次数有硬上限**(不随倍率增长)。
- 返回时合并总结质量可接受(抽样评审通过);不得出现明显的流水账或事实编造。
- 限速队列优先级生效:周反思不被每日 digest 饿死。
- 回归:现有 digest / weekly 测试(`test_life_digest.py`、`test_life_phase24.py`)在 `rate=1.0` 下行为不变。
