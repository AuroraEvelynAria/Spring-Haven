# ADR-016: 故事脊椎与节拍——让「有事可做」由状态驱动，而不是写一棵剧情树

* 状态: **草案**(2026-10-16 提出;实现前须评审)
* 动机来源: 用户体感"仍然像聊天机器人、无事可做",提出"引入线性但存在分支的故事"

## 背景与问题

当前的体感问题已在 2026-10-16 的 UI 审计中定位:

1. **她的生活在数据里,不在事件里**——`life_events`(带 `world_occurred_at`)、每日 digest、夜织摘要都在库里,但主界面只有"此刻生活"一句话与四个数字;
2. **只有你说话,世界才发生**——`current_intent`(planned/executing)已存在,却没有任何后果(在做饭也不会回应得慢);
3. **她的决定不是她做的**——规则算数值、模型只做旁白,于是"驱动"退化成"设定"。

第 1、2 条让用户**看不到生活在推进**;第 3 条让推进**没有方向**。"引入故事"要解决的正是后者:给时间一个形状,让"她正在经历什么"成为可感知、可参与、可回忆的东西。

## 方案对比

| | A. 剧情树(视觉小说式分支) | B. **剧本脊椎 + 状态演绎**(推荐) | C. 纯涌现(无作者结构) |
|---|---|---|---|
| 结构 | 预先写好的分支节点图 | 作者写**节拍链**(线性脊椎)+ 少量**枢轴选择**;每个节拍的具体演绎由状态决定 | 无;全部由 agent 自主产生 |
| 内容来源 | 作者文本 | 节拍=作者写的**条件与意图**,台词/描写由 LLM 依据**她自己的记忆与处境**生成 | LLM 全权 |
| 分支形态 | 显式选择(选 A 走 A 支) | **状态分支**为主(关系/记忆/心境不同→同一节拍不同演绎)+ 少量显式枢轴 | 涌现 |
| 单人可维护性 | 差(内容量按分支指数涨) | **好**(节拍数线性,演绎无限) | 不适用(无内容) |
| 与"AI 驱动"身份 | 冲突(变成剧本播放器) | **一致**(作者给骨架,她给血肉) | 一致但缺少节奏保证 |
| 成本 | 作者工时高 | 每节拍几次 LLM 调用,可离线合并 | 运行时成本最高 |
| 风险 | 退化成视觉小说、与记忆系统脱节 | 需要精心设计触发条件与护栏(见下) | 无事可做的问题不解决 |

**决策倾向:B**。理由:它把"线性但存在分支"精确化为 **脊椎(线性节拍链)+ 枢轴(少量显式选择)+ 演绎(状态驱动的展开)**,既给出节奏与目标感,又不与"她的记忆归她所有、她的生活由机制驱动"的定位冲突;而且 A 的内容量对单作者不可持续,C 不能保证"有事可做"。

## 数据模型(草案)

```
plots(剧本)
  id, save_id, title, spine: [{beat_id, ...}], created_world_day
  # 一个存档可同时挂多条脊椎(主线/角色线),但同一时刻只推进"当前节拍"

beats(节拍,作者手写;Markdown + front-matter 或 JSON)
  id, plot_id, order, title
  enter_when:  进入条件(见下"条件语言")
  goal:        她在这个节拍里的意图(给 LLM 的一句动机,不是给玩家的任务)
  beats_ttl_world_days: 超时(过了多久自动推进/放弃)
  exit_when:   推进条件;或 expires_into: 未达成时的去向
  on_exit:     后果(写记忆/改关系/解锁节拍/触发事件)

beat_state(运行时,按存档)
  plot_id, current_beat_id, entered_world_day, satisfied: {cond_id: bool},
  branch_taken, history: [{beat_id, entered, exited, resolution}]
```

**关键设计:节拍是"她的心事",不是"玩家的任务"。** `goal` 描述她想要什么,玩家可以参与、可以无视;节拍按 `beats_ttl_world_days` 自己往下走(她不会因为你不理她就冻结)。这一条是防止退化成"任务清单"的核心护栏。

## 条件语言(触发与推进)

条件必须**可判定、可复现**,数据源全部来自已有系统:

| 类别 | 例子 | 数据源 |
|---|---|---|
| 世界时间 | `world_day >= 12` | `journey_clock` / `world_time` |
| 生理/心境 | `mood < 35`、`stress > 70`、`awake < 25` | 已有 stats |
| 关系 | `intimacy >= 60`、`intimacy < 30` | 已有 stats |
| 记忆 | `has_memory(tag=排练, min_importance=0.6)`、`claim(subject=主人, predicate=喜欢, object=X)` | Heartloom(检索/主张层) |
| 事件 | `life_event(role=ling, kind=cook, within_world_days=3)` | `life_events` |
| 玩家行为 | `action_count(hug, within_world_days=7) >= 1` | 互动事件 |
| 合成 | `all(...)`, `any(...)`, `not(...)` | — |

**不做的事**:不允许条件里出现自然语言判断题(那会变成"许愿")。若某个条件必须靠语义判断,才交给判定层(未来的 small-model judge),且必须同时给出**保守的规则兜底**。

## 与现有系统的接口

```
世界时钟 tick(已有) ──→ 节拍求值器(新增,纯规则,零 LLM)
                          ├─ 满足 enter_when → 切换 current_beat,写一条 life_event(kind=plot)
                          ├─ 满足 exit_when / 超时 → on_exit(写记忆、改关系、解锁)
                          └─ 暴露给 UI:"她的心事:…(第 N 天起)"+ 时间线一条
当前节拍.goal ──→ 组装进对话提示词("你最近在忙的事")
对话/自主行动发生 ──→ 关键节点写回 Heartloom(带 beat_id 标签供检索)
```

* **不引入新循环**:节拍求值挂在已有的离线调度与 `_process` 刷新路径上;
* **离线友好**:求值是纯规则(零成本),LLM 只在需要**演绎**时调用——与 [ADR-006](ADR-006-offline-residency-throttling.md) 的分工不冲突,反而是它在叙事层的应用;
* **记忆优先**:节拍推进产生的记忆与普通记忆同构(走同一写入路径与指纹),不使用独立的记忆库。

## 验收判据(可证伪)

1. **可推进**:21 世界日内,单条脊椎至少推进 3 个节拍,且每个节拍的进入/退出都能在 `beat_state.history` 里追溯到世界日;
2. **可复现**:给定存档与随机种子,同一条件序列产出同一 `beat_state`(求值器为纯函数);
3. **有分支**:同一节拍在"关系高 / 关系低"两种存档下演绎不同(台词或后续节拍不同),且差异可归因到条件而非模型随机;
4. **不空转**:任一世界日内,若当前节拍未推进,UI 至少显示一条与节拍相关的**她的自主行为**(来自 `life_events`);
5. **不退化**:玩家的无视不会让节拍永久卡死(超时路径必须存在并被测试覆盖);
6. **零污染**:节拍生成的所有记忆/事件都能回溯到 `plot_id`+`beat_id`,清理工具可精确回滚(沿用自主事件那套指纹纪律)。

## 风险与护栏

| 风险 | 护栏 |
|---|---|
| 变成视觉小说(她照剧本念) | 节拍只给条件与动机,台词一律由 LLM 结合**她的记忆**生成;禁止在节拍里写死对白(除非是枢轴的显式选项文案) |
| 变成任务清单(她成了发任务的 NPC) | `goal` 是她的意图不是玩家的任务;超时自动推进,玩家可缺席 |
| 内容量失控 | 首版只做 **1 条脊椎 × 5 个节拍 × 1 个枢轴**;节拍数线性增长,演绎靠 LLM |
| 与规则/LLM 分工原则冲突 | 求值零 LLM;演绎按"是否主观"判据走 LLM;不在节拍层引入按角色分档 |
| 与记忆系统脱节 | 节拍节点的记忆走既有写入路径;`beat_id` 作为标签进入检索 |

## 实施顺序(垂直切片优先)

1. **数据与求值器**:`plots/beats/beat_state` 落地 + 条件求值(纯规则)+ 单测(含超时与分支各一路);
2. **可见性**:dashboard 露出"她的心事(第 N 天起)"与时间线一条(对应本 ADR 动机 1 的"生活在数据里、不在事件里");
3. **演绎**:把 `current_beat.goal` 与相关记忆注入对话提示词,起草"她如何看待自己当前的处境";
4. **枢轴**:实现唯一个显式选择点(两选项,各自 `on_exit` 不同);
5. **验收**:按上面 6 条判据写诊断脚本,进 CI;
6. 再谈第二条脊椎与内容扩产。

## 修订 1(2026-10-16):参考 Asamana 的三件套——张力源 / 导演注入 / 红榜判据

用户要求"参考有剧情的那个项目"(dreamscroll-lab/asamana)。读其源码后确认:**它同样不写剧本树**,而是三件机制的组合,其中两件值得直接借用。

### 1.1 他们是这么做的(已核实)

| 机制 | 位置 | 实质 |
|---|---|---|
| **主题 → 世界/阵容** | `world/builders/theme_analyzer.py`、`cast_designer.py` | 输入一个主题,由 LLM 生成人物/实体/NPC 种子与初始关系(带阵容规模、重要度、性别的归一化约束)。所以"剧情"来自**张力源**,不来自剧本 |
| **导演台(注入)** | `engine/director.py` | 导演说一句自然语言 → 由 LLM(温度 0.2,自述"translation, not creation")翻译成 `DirectivePlan`:`broadcast`(世界级公告)/`message`(定向消息)/`mutations`(≤5 条世界改动:实体状态、生成、移动、生理、状态)。提交时校验并**回报拒绝理由**;`InjectionLedger` 记流水;`Author` 区分是谁注入的 |
| **质量审计** | `tuning/audit_metrics.py`、`audit_criteria.yaml` | 7 维(人设/因果/行动效力/收束 4 基础 75% + 戏剧张力/涌现惊喜/角色成长 3 质量 25%),每维的判据写成**失败模式清单**(红榜),分 scope 汇总并报 coverage |

**其中一条不变量最值得学**:`mutations` 里**任何一条世界改动都必须携带 `observation`——受影响的角色第一人称感知到的文本**,没有 observation 的改动在解析阶段就被丢弃。也就是说:**导演只能通过"她能感知到的东西"改变世界**,世界的变化对角色而言永远是经历,而不是设定。

### 1.2 我们借什么

**(a) 最小导演注入层**(排在原实施顺序 1 之后,简称 1.5):

```
director 输入(打字或菜单)──→ 翻译为"注入请求"(不做世界级 LLM 翻译,先只支持节拍级):
     { beat_id | event_kind, target_role, observation(必填,第一人称可感知文本),
       on_commit: [记忆写入 / 数值增量 / 解锁] }
  ├─ 校验:observation 非空、beat 存在于脊椎、target_role 合法
  ├─ 提交:写一条 source=director 的 life_event + 按 on_commit 结算
  └─ 记账:director_ledger(谁、何时、改了什么) → 可审计、可回滚、可重放
```

* **为什么必须有**:录演示视频时不可能等 20 个世界日——导演台让作者**当场把剧情推到位**;
* **为什么必须带 observation**:防止"导演一按,她的数值变了但她没感觉"——那正是"设定感"的来源;
* **账本**沿用既有纪律:注入可精确回滚(与自主事件指纹清理同一套思路)。

**(b) 红榜式验收判据**(从他们的失败模式里挑适用于二人日常的):

| 借用判据(失败模式) | 落到我们的哪条 |
|---|---|
| **空头约定**:"定下将来要做的事却只给相对指称,目标身上没有到期标记" | 节拍的 `beats_ttl_world_days` 与 `exit_when` 必须把**任何承诺**变成带到期标记的目标 |
| **金鱼脑失忆 / 情绪跨步无诱因突变** | 节拍推进必须写回记忆(`on_exit` 的记忆条目),否则视为断链 |
| **人设漂移 / 越过硬约束** | 演绎不得让她做"人设写明绝不为之"的事(例:小玲的傲娇不允许直白承认怕雷) |
| **戏剧张力不足**(他们的质量维度之一) | 纯甜日常会低分:每条脊椎至少一个**真冲突**(秘密、两难、时间挤压),不能只有温馨 |
| **收束与兑现** | 脊椎必须有终点:节拍要么兑现、要么明确放弃(不得无限挂着) |
| **信息不对称的正当化**(他们的细则) | "决策时目标在场、执行时已离场"不算断链——我们判分时同样不该把这类时序差算作 bug |

### 1.3 我们不照搬什么

* **他们的戏剧来自多角色社会博弈**(权谋、背叛、群体冲突);我们是 **2 个角色 + 玩家**,戏剧必须**内向的**:秘密(怕雷)、角色间的两难(姐姐的调度者过载 vs 妹妹的梦想)、时间与学业的挤压、以及"玩家缺席"本身。照搬权谋会把人设写崩;
* **他们的 7 维权重按群体世界标定**,我们借其**失败模式**,不借其权重与分数体系(我们的规模下 coverage 与 scope 划分无意义)。

### 1.4 对实施顺序的影响

原顺序 `1 数据与求值器 → 2 可见性 → 3 演绎 → 4 枢轴 → 5 验收` 调整为:

```
1 数据与求值器 → 1.5 最小导演注入层(含账本) → 2 可见性 → 3 演绎 → 4 枢轴 → 5 验收(含红榜判据)
```

理由:1.5 同时服务于两个当下需求——作者不必等世界日就能推进剧情,以及演示视频的可控节奏;而且它只依赖 1 的数据结构,不引入新循环。
