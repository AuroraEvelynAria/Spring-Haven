# ADR: WS 推送设计补全 —— 鉴权、乱序防护、推送粒度、降级粘滞

- 状态:**草案(仅设计,未实施)**
- 关联:issue #28(本单)、#23(world_time 单调序号)、#24(前缀缓存)、#26(驻留期零推送)、#22;`godot/docs/WorldTimeArchitectureReview.md`、`godot/docs/CompanionCoreReliability.md`
- 决策范围:`companion-core/src/spring_haven_core/app.py`(路由与生命周期)、客户端 `godot/scripts/autoload/CompanionCoreClient.gd`

## 背景

### 现状:没有推送,只有轮询 + 心跳

- Core 是**纯 aiohttp HTTP 服务**(`app.py` 的 `add_get` / `add_post`),**不提供 WebSocket 服务端**;
- 唯一的 WS 是**对外**的 TTS 供应商客户端(带 `ClientWSTimeout`,见 #3),与本项无关;
- Godot 每 **60 秒**向 Core 同步一次双角色身体状态(心跳);
- Core 只在**心跳停止 ≥ 3 分钟且用户空闲 ≥ 30 分钟**后才自行开始离线推演(`CompanionCoreReliability.md:30`)。

### 设计草案的内在矛盾

设计意图是「**无变更无通信**」,但生理状态是**连续衰减**的 —— 浮点数每 tick 都在变。
若不定义**推送粒度**,「有变更就推」会退化成高频流(每秒数十条),在移动端直接变成耗电与流量问题。

## 决策

### D1 握手鉴权

- 客户端以 `X-API-Key` 完成握手鉴权(与现有 HTTP 路径同一凭据来源);
- 鉴权失败立即关闭连接,**不返回任何状态数据**;
- 凭据不得出现在 URL query 中(避免进日志)。API key 在展示/日志中一律脱敏。

### D2 心跳

- 应用层心跳(不与 TCP keepalive 混为一谈),承担两件事:
  1. 检测半开连接;
  2. **告诉 Core「玩家在场」**,从而抑制 #26 的驻留合并 —— 心跳一停,驻留计时开始。

### D3 单调序号:以 world_time 为准

- 每个推送事件携带 `world_time`(或由它派生的单调序号);
- **乱序防护**:晚到的旧 `world_time` 快照**直接丢弃**;
- 这条同时解决「WS 事件」与「降级 HTTP 轮询快照」之间的乱序 —— 两条通道共用同一序号空间。

### D4 降级粘滞

- WS 断开时降级为 HTTP 轮询;**降级切换必须粘滞**:
  - 一旦降级,至少保持一个完整轮询周期才允许回到 WS,避免通道抖动;
  - 回切需 WS **连续成功若干次**(如 2 次)才生效。

### D5 推送粒度:分桶翻越 / 事件,不推浮点抖动

- **推送触发**(只有这两类):
  1. **分桶翻越** —— 与 #29 / ADR-002 的定性分桶同源:某 `(role_id, stat)` 跨过分桶边界;
  2. **事件 delta** —— 产生 `state_events` 级别的事件(交互结算、里程碑等)。
- **不推送**:连续衰减造成的浮点抖动。
- **UI 侧插值**:两次推送之间,客户端用**已知的衰减速率**本地插值显示;
  推送只做**校准**(类 NTP 校时,而非逐帧同步)。
- 效果:通信量从「每 tick」降到「每次翻越/事件」,同时保持显示连续。

### D6 单实例约束(书面化)

- 「同一时间只运行一个 Godot 客户端实例」写入文档(承 `WorldTimeArchitectureReview.md` ADR-3);
- 多实例 / 多客户端协议(连接声明、WS 广播、会话所有权)列为**中长期**项,不在本 ADR 范围。

## 未决项(需用户裁决)

1. 推送通道与 #27 的会话层如何对应?是否按 `session_key` 分通道?
2. 插值用的「已知衰减速率」由谁下发 —— 快照里带 `decay_scales`,还是客户端本地常量?
3. 乱序丢弃是否需要计数上报(便于诊断通道质量)?
4. 降级粘滞的参数(轮询周期 / 回切成功次数)取多少?
5. 是否需要在 D5 之外允许「强制全量推送」(仅调试用)?

## 备选方案(已否决)

| 备选 | 否决理由 |
|---|---|
| 保持纯 HTTP 轮询,不做 WS | 轮询周期要么太慢(状态滞后)、要么太快(等同高频流),无法同时满足实时性与通信量 |
| 逐 tick 推送浮点状态 | 与「无变更无通信」的意图直接矛盾,退化为高频流 |
| 推送完整状态快照而非 delta | 快照 last-write-wins 会丢增量细节,与 #22 的增量协议冲突 |
| 用 TCP keepalive 代替应用层心跳 | 半开连接检测不及时;且心跳还承担「玩家在场」语义(D2) |
| 降级时不粘滞,立即回切 WS | 通道抖动会让状态显示反复跳变,体验差于稳定轮询 |

## 正面后果

- 通信量由「连续量」变为「离散事件量」,与生理状态的分桶定性化(#29)天然一致。
- `world_time` 单调序号统一了两条通道的次序语义,乱序处理只需一处逻辑。
- 「心跳 = 玩家在场」让 #26 的驻留判定与本项复用同一信号,避免两套在场判定。

## 负面后果

- 客户端要做**衰减插值**,UI 逻辑复杂度上升(插值错了会显示成「状态卡住」或「跳变」)。
- 以分桶翻越作为触发条件,意味着**边界附近**的抖动可能产生成对推送 ——
  需复用 ADR-002 的 `_BucketHysteresis` 做滞回兜底。
- WS 是新增组件,鉴权 / 断线 / 粘滞三类边界都要测,测试面明显扩大。

## 验收

- 握手鉴权:错误 key 被拒,且不泄漏任何状态。
- 乱序:注入晚到的旧快照,必须被丢弃且不改变 UI。
- 粒度:连续衰减**不产生**推送;分桶翻越与事件 delta **各产生一条**。
- 降级:断线进入轮询且在一个周期内不回抖;恢复需连续成功。
- 单实例运行约束写入文档。
